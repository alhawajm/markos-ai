## Media integrity boundaries

Enforce capacity before uploading or starting generation, and recheck at attachment time. The UI must explain why a second attachment is unavailable for Post, Reel, or Story and keep explicit removal available. Carousel-to-single changes with multiple assets must preserve the current type and explain how to remove extras first.

Server enforcement must cover concurrent attachment requests, content-type changes, readiness changes, and generated-media completion after a user changed the draft. An in-flight job must not append incompatible media or overwrite a newer media list from a stale snapshot. Reuse existing stored assets; never silently discard the owner's files to satisfy the count. This pass requires focused API/worker tests as well as browser tests; the UI-only checkpoint below does not establish these guarantees.

The implemented shared rules count stored media IDs, including unavailable assets. The editor exposes removal for those unavailable IDs so legacy records can be repaired. Actual incompatible type changes fail atomically; unchanged-type caption saves remain available for repairs. A generated output that cannot attach is retained in the library, with its output ID and a non-retryable recovery outcome. UI conflict refresh must update current media without replacing unsaved caption fields or adopting a newer revision as if the owner had reviewed it.

**Separate existing storage debt:** deleting an unreferenced library asset and attaching it concurrently still use different coordination boundaries. The current delete path checks references before storage deletion and soft deletion; a concurrent attach can race that check. Content-row locking does not solve the complete library deletion lifecycle. Address asset deletion/attachment coordination with a focused recovery design and race test before claiming end-to-end media durability. Existing publication validation still checks availability and metadata; this increment does not replace it.
